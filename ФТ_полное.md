# Функциональное требование (полная версия)
## Сервис учёта склада, бронирования и работы с клиентами для бизнеса аренды посуды

**Версия:** 1.1
**Дата:** 04.07.2026
**Статус:** Черновик для согласования

> **Согласованные решения (v1.1):**
> 1. Аренда рассчитывается **по срокам, посуточно** (стоимость = число суток × суточная цена аренды).
> 2. Онлайн-оплата на сайте пока **не подключается** — только заявка + звонок; платёжный модуль добавим позже.
> 3. Склад **распределённый — несколько точек**; учёт остатков ведётся по каждой точке.
> 4. Нужны **комплекты/наборы** — возможность объединять несколько товаров в одну позицию.

---

## 1. Общие сведения

### 1.1. Бизнес-контекст и проблема
Бизнес предоставляет продукцию (посуду и сопутствующий инвентарь) в аренду. У бизнеса есть собственный склад. Клиенты обращаются по разным каналам связи (звонки, мессенджеры, лично), из-за чего возникает **рассинхронизация бронирований**: один и тот же товар в одном и том же количестве могут забронировать несколько клиентов, иногда уже внеся оплату. В результате возникает конфликтная ситуация — приходится отказывать клиентам, которые уже заплатили.

### 1.2. Цель проекта
Разработать единую систему, которая:
1. Ведёт **актуальный учёт склада** в реальном времени (сколько есть, сколько забронировано, сколько выдано, сколько в пути на возврат).
2. Исключает **двойное бронирование** за счёт единого источника данных о доступном остатке.
3. Ведёт **полную историю операций** с привязкой к сотруднику (кто, что, когда выдал/принял).
4. Даёт клиентам **удобный сайт-витрину** для просмотра и заказа.
5. Имеет **открытый API** и **интеграцию с ИИ (MCP)** для дальнейшего масштабирования.

### 1.3. Состав системы
Система состоит из трёх взаимосвязанных компонентов:

| № | Компонент | Назначение |
|---|-----------|-----------|
| A | **Сервис учёта (Backend + Web-панель)** | Внутренняя система для сотрудников: склад, брони, выдачи, возвраты, бой, аудит |
| B | **Сайт-витрина (Frontend для клиентов)** | Публичный сайт с каталогом, остатками и оформлением заявок |
| C | **API + MCP-слой** | Программный интерфейс для интеграций и работы с ИИ-ассистентом |

## 2. Роли пользователей

| Роль | Описание | Основные права |
|------|----------|----------------|
| **Администратор** | Владелец/управляющий | Всё + управление пользователями, справочниками, ценами, просмотр всех логов и отчётов |
| **Сотрудник склада** | Работник, ведущий операции | Приём/выдача/возврат/бой, создание броней, загрузка товаров, работа с заявками |
| **Клиент (гость)** | Посетитель сайта | Просмотр каталога и остатков, оформление заявки (без входа в систему) |
| **ИИ-ассистент (сервисная роль)** | Программный агент через MCP | Чтение остатков и статусов, ответы на запросы (только чтение или ограниченные действия — см. п.9) |

**Требования к учётным записям сотрудников:**
- У каждого сотрудника **индивидуальный логин и пароль**.
- Все действия выполняются **от имени вошедшего сотрудника** и логируются под него.
- Пароли хранятся в хешированном виде (bcrypt/argon2), поддержка смены пароля.
- Возможность блокировки/деактивации учётной записи без удаления истории.

## 3. Сущности (модель данных)

### 3.0. Точка / Склад (Location)
Физическая точка хранения. Склад **распределённый — несколько точек**.
- `id`, `Название точки`, `Адрес`, `Комментарий`, `Активна (да/нет)`
- Остатки, брони, выдачи и возвраты **привязаны к точке**.
- Сотрудник может быть привязан к одной или нескольким точкам (право работать по точке).
- (Опционально) перемещение товара между точками как отдельная операция.

### 3.1. Товар (Product / Позиция каталога)
Карточка вида товара (например, «Тарелка белая 25 см»).
- `id` — уникальный идентификатор
- `Наименование`
- `Категория` (тарелки, бокалы, приборы, текстиль и т.д.)
- `Артикул / SKU`
- `Тип позиции`: `Товар` или `Комплект` (см. 3.1a)
- `Единица измерения` (шт., комплект)
- `Фотографии` (одна или несколько)
- `Описание`
- `Залоговая (закупочная) стоимость единицы` — используется при расчёте боя
- `Суточная цена аренды за единицу` — стоимость аренды за 1 сутки
- `Признак «показывать на сайте»` (да/нет)
- `Дата создания`, `кто создал` (сотрудник)

### 3.1a. Комплект / Набор (Set / Bundle)
Позиция, объединяющая несколько товаров в одну (например, «Сервировочный набор на 6 персон» = 6 тарелок + 6 бокалов + 6 приборов).
- `id`, `Наименование набора`, `Фотографии`, `Признак «показывать на сайте»`
- `Состав`: список `(товар, количество на 1 набор)`
- **Доступность набора** рассчитывается по самому дефицитному компоненту:
  `Доступно наборов = min( Доступно компонента / Кол-во в наборе )` по всем компонентам.
- При брони/выдаче набора **резервируются/выдаются входящие товары** в нужном количестве.
- Цена аренды набора: либо собственная суточная цена, либо сумма цен компонентов (настраивается).

### 3.2. Складской остаток (Inventory / Наличие)
Актуальное количество по каждому товару **в разрезе точки хранения**. Рассчитывается по формуле:

```
Доступно к брони = Всего на точке
                 − Забронировано (активные брони)
                 − Выдано (на руках у клиентов)
                 − Списано (бой/утеря)
                 + Ожидаемые возвраты (опционально — как отдельный показатель)
```

Отслеживаемые показатели по каждому товару (по каждой точке и суммарно):
- `Всего на балансе` (физически числится)
- `Забронировано` (по активным броням)
- `Выдано / на руках` (сколько сейчас у клиентов)
- `Доступно к брони` (свободный остаток)
- `Ожидается к возврату` (с датами)

### 3.3. Поставка / Завоз (Supply)
Приход нового товара на склад.
- `id`, `Товар`, `Количество`, `Дата завоза`, `Комментарий`, `Кто оформил`
- При проведении **увеличивает** `Всего на балансе`.

### 3.4. Клиент (Client)
- `id`, `Имя`, `Телефон` (обязательно), `Доп. контакты`, `Источник` (сайт / звонок / мессенджер), `Комментарий`
- История заявок и броней клиента.
- Контакты **сохраняются**, чтобы можно было связаться, если товар не вернули.
- **Личный кабинет клиента не предусматривается.** Клиент нигде не регистрируется — при заявке указывается только имя и **номер телефона**. Идентификация клиента ведётся по номеру телефона.

### 3.5. Бронь (Booking / Reservation)
Резервирование товара за клиентом на определённый период.
- `id`, `Клиент`, `Точка выдачи`, `Список позиций` (товар/набор + количество), `Дата начала аренды`, `Дата ожидаемого возврата`
- `Количество суток` = (дата возврата − дата начала), **всегда округляется вверх до полных суток** (неполные сутки считаются как полные)
- `Статус`: `Новая` → `Подтверждена` → `Выдана` → `Возвращена` (частично/полностью) → `Закрыта` / `Отменена`
- `Сумма аренды` = Σ (кол-во × суточная цена × число суток) по позициям
- `Залог` (необязательное поле) — можно указать сумму залога за заказ; поле опциональное
- `Внесённая оплата / предоплата`
- `Кто создал`, `дата создания`
- Активная бронь **резервирует** количество на выбранной точке и уменьшает `Доступно к брони`.

### 3.6. Выдача (Issue)
Факт передачи товара клиенту.
- `id`, `Бронь`, `Список позиций и количество`, `Дата/время выдачи`, `Кто выдал` (сотрудник)
- Уменьшает `Доступно`, увеличивает `Выдано / на руках`.

### 3.7. Возврат (Return)
Факт приёма товара обратно.
- `id`, `Бронь/Выдача`, `Список позиций и фактическое количество`, `Дата/время возврата`, `Кто принял` (сотрудник)
- Возможен **частичный возврат** (вернули не всё).
- Возвращённое количество возвращается в `Всего на балансе` / `Доступно`.

### 3.8. Бой / Списание (Breakage / Write-off)
Учёт битой, утерянной или испорченной посуды.
- `id`, `Связанная бронь/клиент` (если применимо), `Товар`, `Количество`, `Причина` (бой/утеря/износ)
- `Сумма к удержанию` = `Количество × Залоговая стоимость единицы`
- `Кто оформил`, `дата`
- Списанное количество **вычитается** из баланса; стоимость боя учитывается в расчётах по клиенту.

### 3.9. Заявка с сайта (Web Order)
Первичное обращение клиента с публичного сайта.
- `id`, `Имя`, `Телефон`, `Список выбранных позиций и количество`, `Комментарий`, `Дата/время`
- `Статус`: `Новая` → `В обработке` → `Сконвертирована в бронь` / `Отклонена`
- При поступлении: уведомление в сервисе **+ дублирование в Telegram-бот**.

### 3.10. Журнал аудита (Audit Log)
Неизменяемая история всех значимых действий.
- `Кто` (сотрудник), `Что сделал` (операция), `Над чем` (сущность), `Старое → новое значение`, `Дата/время`
- Обязателен для операций: выдача, возврат, бой, изменение цен, изменение остатков, создание/отмена брони.

## 4. Компонент A — Сервис учёта (Web-панель для сотрудников)

### 4.1. Аутентификация и доступ
- Вход по логину и паролю.
- Разграничение прав по ролям (п.2).
- Все действия ведутся под текущим сотрудником и попадают в журнал аудита.

### 4.2. Учёт складских товаров — ввод/заведение
Три способа завести товары на склад:

**4.2.1. Загрузка через Excel-шаблон**
- Система предоставляет для скачивания **готовый шаблон Excel** с колонками (Наименование, Категория, SKU, Ед. изм., Кол-во, Залог. стоимость, Цена аренды и т.д.).
- Сотрудник заполняет и загружает файл.
- Система валидирует данные, показывает ошибки построчно, даёт превью перед импортом.
- После подтверждения — массовое создание/обновление позиций.

**4.2.2. Заведение через мобильный телефон (браузер + камера)**
- Открытие панели через мобильный браузер (адаптивный интерфейс).
- Кнопка «Добавить товар» открывает **камеру телефона**.
- Сотрудник фотографирует товар, фото прикрепляется к карточке.
- Заполняет наименование, количество, стоимость → сохраняет.
- Цель: быстро заводить товары «в поле», прямо на складе.

**4.2.3. Ручное создание карточки**
- Обычная форма создания/редактирования товара в веб-панели.

### 4.3. Учёт количества и движения
Система в реальном времени показывает по каждому товару:
- Сколько **всего** на балансе.
- Сколько **забронировано** и **на какой период** (даты).
- Сколько **выдано / на руках** у клиентов.
- **Когда ожидается возврат** (дата) и **в каком количестве**.
- Сколько **доступно к новой брони**.

### 4.4. Операции движения товара
- **Поставка/завоз** → увеличивает баланс, пересчитывает актуальный остаток.
- **Бронь** → резервирует количество на период.
- **Выдача** → фиксирует передачу клиенту.
- **Возврат** (полный/частичный) → возвращает товар в оборот.
- **Бой/списание** → уменьшает баланс, начисляет стоимость боя.

Ключевое правило: **актуальное количество всегда пересчитывается автоматически** после любой операции (завоз, бронь, выдача, возврат, бой).

### 4.5. Контроль сроков и «висящих» товаров
- По каждой выдаче считается **количество дней, прошедших с момента брони/выдачи**.
- Если срок ожидаемого возврата **просрочен** — товар и клиент подсвечиваются.
- Сохраняются **контакты клиента**, чтобы связаться, если не вернули.
- Отдельный список/отчёт: «Что на руках», «Просрочено», «Ожидается сегодня/на этой неделе».

### 4.6. Работа с клиентами (внутри панели)
- При обращении клиента сотрудник выбирает товары.
- Система показывает по выбранным позициям: **сколько выбрано** и **сколько ещё доступно** на складе.
- Оформление брони с проверкой доступности (защита от двойного бронирования).
- Учёт предоплаты/оплаты.

### 4.7. Расчёты и удержания
- Расчёт суммы аренды **посуточно**: `кол-во × суточная цена × число суток аренды` по каждой позиции. Число суток **округляется вверх до полных суток**.
- **Залог** — необязательное поле: можно указать сумму залога за заказ, но это не обязательно.
- Учёт стоимости **боя** (удержание = кол-во × залоговая стоимость).
- Итог по клиенту: сколько отдали, по какой цене, за сколько суток, сколько вернули, сколько удержано за бой.
- Оплата на данном этапе фиксируется вручную (предоплата/оплата наличными/переводом); **онлайн-оплата — в следующей версии**.

### 4.8. Отчёты (минимальный набор)
- Текущие остатки по складу.
- Что на руках у клиентов / просрочки.
- Движение за период (завозы, выдачи, возвраты, бой).
- Активность сотрудников (кто сколько выдал/принял) — на основе журнала аудита.

## 5. Компонент B — Сайт-витрина (для клиентов)

### 5.1. Назначение
Публичный сайт, где клиент видит каталог и оформляет заявку.

### 5.2. Требования к каталогу
- Показывает **актуальное количество** товаров (остатки берутся из Сервиса учёта через API).
- Показывает **только товары с фотографиями** (и с признаком «показывать на сайте»).
- Оформление в виде **современного меню**: красивая сетка карточек с фото, названиями, ценами.

### 5.3. UX/дизайн
- **Современный, визуально приятный** дизайн.
- **Mobile-first**: удобный просмотр и заказ с телефона.
- Быстрая загрузка, аккуратные фото товаров.

### 5.4. Оформление заявки
Цель сайта — **не полноценный онлайн-заказ, а «лид»**: собрать выбранные позиции и контакт, чтобы **свести клиента к оператору** и продолжить общение по другим каналам связи (звонок/мессенджер).

Сценарий клиента:
1. Просматривает каталог, выбирает нужные позиции и количество.
2. Вводит **имя** и **номер телефона** (без регистрации и личного кабинета).
3. Нажимает «Заказать / Забронировать» → отправляет заявку.

При отправке:
- Заявка **поступает в Сервис учёта** (кто заказал, что, сколько, есть ли в наличии).
- Уведомление **дублируется в Telegram-бот** («Новая заявка по таким-то позициям»).
- Сотрудник видит заявку и **номер клиента**, проверяет наличие, **связывается с клиентом** и обговаривает бронь.
- **Точку выдачи клиент на сайте не выбирает** — её при необходимости определяет сотрудник при оформлении брони.

### 5.5. Обратная связь
- Возможность отметить заявку как принятую/отклонённую (внутри панели).
- (Опционально) статус заявки виден клиенту либо сообщается по телефону.

## 6. Компонент C — API

### 6.1. Назначение
У сервиса должен быть **собственный API-интерфейс**, чтобы к нему можно было **интегрировать другие сервисы** (это одно из ключевых требований).

### 6.2. Требования к API
- **REST (JSON)** архитектура, версионирование (`/api/v1/...`).
- Аутентификация по токенам/ключам (для интеграций) и по сессии (для веб-панели).
- Документация (OpenAPI/Swagger).
- Основные ресурсы: товары, остатки, брони, выдачи, возвраты, бой, клиенты, заявки, отчёты.
- Сайт-витрина работает **поверх этого же API** (единый источник данных).

## 7. Компонент — Интеграция с ИИ (MCP)

### 7.1. Назначение
Ключевое требование: возможность работы с **искусственным интеллектом**. Для ИИ нужно сделать **MCP-сервер**, чтобы ассистент «видел» состояние склада и мог отвечать на вопросы.

### 7.2. Что должен «видеть» ИИ через MCP
- Какое количество товара **сейчас доступно**.
- Какое количество **вернулось**.
- Какое количество **до сих пор у клиентов** и **когда должны вернуть**, **в каком количестве**.
- По **какой стоимости** отдали и по **какой цене**.
- Что есть на складе / чего нет / какие товары есть.

### 7.3. Возможности ИИ-интерфейса
- Через интерфейс можно **опрашивать** склад на естественном языке: «что есть на складе», «сколько свободных бокалов», «что просрочено».
- Ассистент **ищет и показывает** ответ, чтобы сотрудник не искал вручную по складу.
- Инструменты MCP (примерно): `get_stock`, `get_available`, `get_on_hands`, `get_returns`, `get_overdue`, `search_products`, `get_client_debt`.
- Для операций записи (если понадобятся) — с явным подтверждением и логированием.

## 12. Согласованные решения и открытые вопросы

### Согласовано
1. ✅ Аренда — **по срокам, посуточно**; число суток **округляется вверх до полных суток**.
2. ✅ Оплата — пока **только заявка + звонок**; онлайн-оплата подключается позже.
3. ✅ Склад — **несколько точек**; учёт по каждой точке.
4. ✅ **Комплекты/наборы** — товары можно объединять в одну позицию.
5. ✅ **Личный кабинет клиента не нужен** — только имя и номер телефона, без регистрации.
6. ✅ **Залог** — необязательное поле: можно указать, но не обязательно.
7. ✅ **Точку выдачи клиент на сайте не выбирает.** Задача сайта — свести клиента к оператору; дальше общение и оформление ведёт сотрудник.
